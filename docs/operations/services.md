# Site, social, support, and email

The game remains at `/`. Public routes are `/about`, `/news`, `/news/:slug`, `/help`, `/help/:slug`, `/help/contact`, `/help/requests`, `/feedback`, `/privacy`, and `/terms`. Public articles are rendered by Express without guest creation, sockets, or Phaser.

The `/banned` page distinguishes permanent bans from temporary account suspensions. Temporary suspensions show a live countdown using the lobby's shared formatter and animated pixel clock (`public/scripts/restrictionClock.js`); the local end date is available on hover. At expiry, the page verifies access through `/status` before returning to the lobby; periodic checks also pick up an administrator lifting the restriction. Both states link to Contact Support and the Help Center. Bans and temporary suspensions preserve login sessions: members can create support requests, read their own conversations, and reply. Restricted accounts can also log in again for support, including through a support return link. Lobby, party, game pages, gameplay APIs, and sockets continue to reject restricted accounts; active game/lobby sockets disconnect and navigate to `/banned`. Reduced-motion settings stop the clock animation while keeping the countdown current.

## Content and release configuration

Edit `content/manifest.json` for News and Help titles, slugs, summaries, categories, dates, and artwork. Add the corresponding Markdown file under `content/news/` or `content/help/`. Use plain Markdown; raw HTML is disabled. Deploy the `content/` directory alongside `src/` and `dist/`, and restart the server to reload the manifest. Do not use unannounced or invented release claims. News uses the newest story as the lead and groups the remaining stories alongside it. Keep news stories to a few brief paragraphs and use the opening paragraph as the manifest summary so cards show an actual excerpt. Cards show the date, one pixel headline, the preview, and a “Read more” link with a pixel arrow. Article pages stack the meta line (date, reading time), the headline and then the full-width artwork, followed by the body, a play call-to-action and “More stories” using the same cards as the News page; the card preview is not repeated. Existing slugs and publication dates should stay stable when editing copy.

`content/legal/privacy.md` and `content/legal/terms.md` are the legal source documents served by the application. Changes to policies or operator details require a deliberate content/version update; implementation notes do not establish legal compliance.

`src/shared/site/siteConfig.json` owns the release name (`beta v1.1`); the site menu adds the automatic build number and deployment status described in [Deployment](deployment.md#automatic-build-versions). It also owns document versions, support contact, and retention durations. Increment document versions when seeking renewed acceptance. No date of birth or age eligibility step is implemented. The Terms state a 13+ audience and guardian-permission requirements.

Signup records acceptance of both document versions atomically with conversion of the guest account. Existing and guest players accept when first pressing Ready, then continue into matchmaking. Lobby sockets can connect before acceptance; Ready, queue entry, and game-data access require current acceptance. Public information and support remain available separately. Already connected players may finish a match during a deployment; a reconnect uses the current server versions.

Public pages share `src/client/site/pages.css`: lobby-style framed panels, ink-ringed cards, chroma buttons, pixel headings and the logo's orange accent. There are no small labels above headings. Text links use a dashed pixel underline that a solid darker-blue bar wipes across on hover; uppercase pixel links get the wipe alone. Sections below the fold settle in once as they scroll into view (`siteMotion.mjs`, off with reduced motion); content already on screen at load never animates, and nested items never animate inside a moving section. `site.css` keeps only the chrome the lobby also uses (header, menus, settings and legal dialogs). The pixel-font footer carries the game, support and legal links and no version number.

Navigation between public pages keeps the header pinned with a brief cross-document view transition; fonts are preloaded, the page reserves its scrollbar gutter, and the header's account control stays hidden until the session (or the last session cached in `sessionStorage`) fills it, so “Log in” never swaps to a name on screen. Support pages reserve their loading height so the footer doesn't jump.

Help and News Markdown supports game components from `src/shared/site/markdownComponents.cjs`: `{gems:50}`, `{coins:150}` and `{trophies:250}` render currency chips; `{path:Profile > Account > Change Name}` renders a highlighted click path; `{key:Space}`, `{key:Left}` and `{mouse:left}` render inputs; a blockquote starting `[!TIP]`, `[!NOTE]`, `[!WARNING]` or `[!REWARD]` becomes a callout. Help search indexes the plain-word form. The Help Center groups articles in compact flowing topic columns. Topic and article headings use the shared pixel font; summaries use the reading font. Keep long titles wrapping within their cards and reserve the full search-status line so the activity indicator does not move the content below it.

The About page is assembled by `src/server/services/site/aboutPage.js`; its scoped layout and gameplay reel live in `src/client/site/about.css` and `aboutReel.mjs`. The About hero puts the wordmark over the lobby sky. Its muted reel plays the clips in `src/shared/site/aboutClips.json` start to finish, one after another, looping back to the first; there is no picker, the header shows only the mode, and a small translucent button pauses it. “Meet the Bros” (`aboutBros.mjs`, `spriteLoop.mjs`) uses the lobby's character cards as tabs and each Bro's real idle animation from its game spritesheet, standing on a lobby platform (the walkable top is measured from the art) in front of that map's lobby sky; each Bro gets the next map in turn. Its stats are the lobby's character-detail stat boxes (Health, Attack, Super with icons and segmented tracks) and the animated level badge, using the real health, damage, super damage and coin prices from `characterStats`. Panels share one grid cell so the box never resizes. Until a visitor takes over it levels each Bro to the cap and moves to the next. Levelling shows a pixel aura around the badge (no bounce), and switching Bros eases the old stage out, loads the next map's art, then eases it back in while the sky cross-fades. Below it: the Trophy Road (`aboutRoad.mjs`) pins its heading and road while you scroll along the real track from `buildTrophyRewardTrack()` (every milestone except player cards and unplayable modes, plus one coin or gem cache between each pair, with art from the shared `src/shared/currencyRewardArt.cjs`); each milestone switches from Locked to Claimed with the lobby's card burst and pixel sparks. “Make it yours” (`aboutCosmetics.mjs`) is a static collection grid of real catalog items (player cards with a Bro in the card window, skins, wide titles, profile icons) where one tile at a time swaps to another item of its kind. “Play with friends” (`aboutFriends.mjs`) plays a scene in the game's chat beside a mini lobby: the friend comes online, joins, readies up, the party searches and a match-found popup appears. Section copy never names a count of fighters, modes or arenas. Site cards use the lobby's mode/map card frame: art inset inside a padded card, uppercase pixel titles, a 2px lift on hover. It plays only while visible, honors reduced-motion and data-saving preferences, and uses local MP4 clips plus JPEG posters from `public/assets/site/gameplay/`. The clips are real bot matches (1v1, two 2v2s and a Bank Bust 3v3) recorded from the game client. `scripts/art/record-about-gameplay.cjs` records each take from the game's Super High render at 60 fps (it refuses a take that drops frames or would need upscaling), keeps the camera on one fight at a time, and cuts the eight seconds with the most hits, supers and knockouts from the server's event log. The poster is the busiest moment of the cut. It needs a local Chromium and FFmpeg; review takes and event logs stay in `output/about-gameplay/`, and `--cut` re-cuts saved takes. Candy Land cannot hold 60 fps at capture resolution on the development Mac.

## Search discovery

Public pages include descriptions, canonical links and social previews when `PUBLIC_BASE_URL` is set to the production origin. `/sitemap.xml` lists the lobby, public informational pages, and manifest-backed news and help articles; `/robots.txt` advertises it. Account-specific support pages are excluded and marked noindex. The sitemap returns 503 when the origin is missing or invalid rather than publishing URLs based on an untrusted request host. Set `PUBLIC_BASE_URL` to the actual public HTTPS origin in production, then verify the sitemap and submit it to search engines if desired. Search engines decide whether and how to index and display pages.

## Database and API

Admin console APIs (`/api/admin/*`), including support and feedback triage, are exempt from gameplay HTTP rate limits, matchmaking suspensions, and support request rate limits. Every endpoint still requires an authenticated administrator; ordinary gameplay and player support limits apply when an administrator uses those player-facing APIs.

Run `node scripts/db/apply-migration.cjs site` before starting this release. See [database setup](database.md) for prerequisites and migration order. Startup verifies all three tables. Existing accounts, balances, and matches are preserved.

- `POST /api/feedback`: authenticated guest/member feedback; subject, message, submissionKey. The confirmation offers only a way back to the game. Feedback has no topic and is stored with category `feedback`; the admin feedback inbox has no category filter. Support requests keep their topics (account, purchase, bug, gameplay, safety, privacy, other), so ideas go to Feedback and problems go to support. A new support request opens straight into its conversation in My requests. Its request list is the lobby's Friends drawer (`friends.css`: header, All/Open/Active/Closed tabs, rows with topic icons) and the conversation uses the in-game chat styles from `chat.css`.
- `GET/POST /api/support/requests`: permanent-account conversation list/create.
- `POST /api/support/reports`: authenticated guest/member profile reports with `targetUserId`, a reason from `src/shared/social/profileReports.json`, message (5–3500 characters), and `submissionKey`. The server rejects self-reports and missing players, resolves the target's current name and account ID, and saves them with the reason in a support request under **Reports**. Reports use the existing same-origin, rate-limit, notification, idempotency, and retention rules; no migration is needed. Members can follow replies in My requests; guests have no reply channel. Expanded profiles show the report flag beside the friend action except on your own profile or when opened from the leaderboard.
- `GET /api/support/requests/:id`, `POST /api/support/requests/:id/messages`: owner-only reading and replies.
- `/api/admin/feedback` and `/api/admin/support`: administrator-only lists and details; `POST /:id/status` changes triage state. `POST /api/admin/support/:id/messages` replies. The admin composer is a single-line reply field; sending a reply does not close the request. Change its status using the conversation header controls.
- Admin report rows include the target's saved report count and distinct reporters. Opening a report adds the target's current account link, total and 30-day counts, distinct registered reporters in that window, and the latest ten reports. History follows the stable account ID in server-generated report subjects, including reports saved before this feature and before name changes; no migration is needed. Counts cover retained requests, not deleted history, and ignore reply counts. `src/server/services/site/profileReportReview.js` owns the advisory rule: three distinct registered reporters within 30 days suggests considering punishment after reviewing evidence; repeated or guest reports suggest investigation; a limited recent history suggests no punishment yet. These are unverified allegations and distinct accounts do not establish distinct people. A confirmed violation may still justify action on a single report. Closing a request is triage only, not a finding of guilt. Recommendations never apply penalties; use the reported player's Account controls after review. Report statistics and recommendations are admin-only.
- `POST /api/admin/grant`: administrator-only. Adds or removes `coins` and `gems` (whole numbers, up to 10,000,000 each way) for `userId` or up to 50 `userIds` in one transaction, with an optional `note` of up to 40 characters. Balances stop at zero. Each applied change is written to `shop_currency_ledger` with `source_type = 'admin_grant'`. `GET /api/admin/grants` lists the latest 30.
- **Players** shows `users.last_seen_at` in the directory and in the tags below the player's name, alongside account type, presence and join date. The header and plain stats row share one frame. Accounts without recorded activity show “Unknown”; account edits do not count as player activity. `GET /api/admin/users/:id` includes all completed match totals, wins, losses, explicit draws, win rate (wins divided by all completed matches, including draws), current streak and cosmetic inventory. Legacy battles without a recorded outcome remain in the total. Highest streak comes from the user row.
- **Players → Inventory** edits skins, profile icons, player cards and titles. `POST /api/admin/users/:id/inventory` accepts `{changes: [{kind: "skins"|"icons"|"cards"|"titles", id, owned: true|false}]}`. Only listed items change, preserving concurrent grants of other items. Automatic unlocks/defaults cannot be revoked. Removing an equipped item selects an owned fallback (or clears an equipped title). Inventory changes and the acting admin/before values are saved atomically in `user_abuse_events` as `inventory_edit`. Missing cosmetic tables disable only their inventory group; titles require the `titles` migration.
- **Players → Activity → Set win streak** uses `POST /api/admin/users/:id/streak` with `{streak}` (integer 0–10,000). It changes the newest N completed battles with a recorded team winner into wins and the preceding decisive battle, if present, into a loss. Draws and unknown outcomes stay unchanged; insufficient decisive history is rejected. Winners and battle summaries change together, affecting every participant's history, statistics and current streak. Stored highest streaks may increase for affected accounts but never decrease. Existing currency, trophies and reward receipts are not replayed. The UI confirms the shared-result effect before saving. The changes and prior winners are recorded atomically as `streak_edit` events with the acting admin ID.
- Account restrictions in **Players → Account**: `POST /api/admin/user-ban` takes `{userId, reason}` for a permanent ban; `POST /api/admin/user-suspend` also takes `durationMinutes` (1–525,600) for a temporary suspension; `POST /api/admin/user-unban` takes `{userId}` to lift either restriction. All require admin access. Ban/suspension reasons are required, up to 220 characters. Restrictions and moderation events (including the acting admin ID and expiry) save in one transaction before disconnecting the player's active sockets. Self-restrictions are rejected. A suspension cannot downgrade a permanent ban; lift it first. Repeated permanent bans preserve the existing reason/event. Suspensions use the same banned messages and page, with an expiry time; account checks lift them at their deadline without a cleanup job, including after restarts. Signed browser holds recheck current account state so unbans also take effect immediately on the next request; an open banned page rechecks every 15 seconds and returns to the lobby when access is restored. Apply `npm run migrate:apply -- temporary-bans` before deploying.
- `GET /api/admin/shop/catalog` and `PUT /api/admin/shop/catalog`: administrator-only shop editor. `GET` returns the catalog JSON, its `revision` and the skins, cards, profile icons, titles, banners and tab icons to pick from. `PUT` takes `{catalog, revision}`, returns 409 if the file changed since that revision and 422 with `errors` if the catalog fails the runtime shop validation, otherwise writes `src/shared/catalogs/shopCatalog.json` and reloads it. On a deployed server that file then differs from git, so commit it or copy it back before the next pull. `GET /api/admin/shop/status` returns rotations, recent orders and Stripe readiness. `POST /api/admin/shop/preview` takes `{catalog, weeks, days}` (offsets up to ±52), validates the draft without writing anything and returns `errors` plus what a new player would see (`sectionMeta`, `sections`, built by the same code as the shop). If the preview cannot be built it still returns `errors` with `previewError`.
- **Store** edits a local draft and publishes it in one step. Every change is checked against the server rules within half a second; problems link to the offer, reward or section they belong to, and Publish stays disabled until there are none. **Live preview** renders the real shop cards for any week or day ahead; clicking a card opens its editor. **Offers** has a card view (lobby cards with this week's status) and a table for quick price, section, sale and order edits. The offer editor only enables offer types that fit the rewards, sets weekly sale membership, and shows the sale price and bundle value as you type. **Weekly rotation** lists four weeks of Sales and rotating sections. **Sections** sets each section's rotation, layout, rows, rarity, owned-item hiding and Expand button. Unpublished drafts are kept in the browser per catalog revision and offered back on the next visit.
- **Runtime** validates reward multipliers (above 0, at most 10) and a coin floor no higher than the ceiling, in the page and in `POST /api/admin/runtime`. Admin sections and open players are reflected in the URL hash (`#store`, `#players/42`).
- `GET /api/site/session`: signed-in state and unread support count, without creating a guest.
- `GET /api/legal/status`, `POST /api/legal/accept`: current document acceptance. `accepted` must be literal true, with matching `termsVersion` and `privacyVersion`.
- `GET /api/site/legal/:kind`: shared legal markup for popups.
- `queue:leave` now optionally acknowledges `{ok:true|false}`; existing callers without an acknowledgment remain supported. Site navigation waits for confirmed queue cancellation.

Writes require browser same-origin Fetch Metadata or a matching Origin header; cross-site requests are rejected. Set `PUBLIC_BASE_URL` to the actual browser origin (or leave it unset locally so the request origin is used). All request ownership and authorship comes from authenticated sessions. Members cannot read other members' conversations. Submissions are plain text, with subject 3–120 characters and message 5–4000 characters. Idempotency keys prevent retry duplication. Guest feedback has no reply channel; durable support requires an account.

Feedback is removed after 12 months. Closed support is removed 12 months after closure; open conversations remain until closed. Hourly cleanup deletes at most 1,000 parent records per run, with message cascade deletion. Support does not accept attachments. When email is configured, new requests enqueue owner notifications; replies are read in the support interface. Privacy requests and password-recovery help are manual through the provided support email; do not promise automated fulfillment.

## Browser preferences

Settings use `bb_settings_v1` in local storage and synchronize between same-origin tabs. They remain device-local. Sensitivity is a multiplier on existing aiming tuning; defaults preserve the prior behavior. SFX applies to Phaser effects and UI audio. Background volume separately controls map and sudden-death music, including active tracks.

Opening a Settings or legal dialog releases pointer capture and suppresses local combat/movement input; it does not pause an online match. With automatic hiding disabled, movement keys do not capture the cursor; clicking the arena still does.

Streamer mode obscures known username labels using pixel mosaics, supplies neutral accessibility labels, and hides battle HUD/canvas name text. Existing lobby code reads DOM text as identity, so original DOM strings are retained as application data under the opaque presentation. It is a screen-sharing feature, not anonymization: it does not hide network data, developer tools, or names typed inside free text. Admin support messages and free-text reports may also contain names.

## Email configuration and delivery

The profile Account area supports Add Email Address / Change Email Address. A permanent, authenticated account can request a six-digit code. Codes expire after ten minutes, allow five guesses, are HMAC hashed, and are consumed on verification. Verified addresses are unique and are never included in public profile responses. Sending is limited to once per minute and five times per hour per account, plus an IP limit. Email does not yet provide password recovery.

Server configuration: `RESEND_API_KEY` (or existing `EMAIL_API_KEY`), `EMAIL_FROM` (default `Bro Battles <noreply@brobattles.dev>`), `EMAIL_NOTIFICATIONS_TO` (owner inbox), and optional `EMAIL_VERIFICATION_SECRET` (defaults to `COOKIE_SECRET`). Keep these server-side. Production needs the same variables separately if it uses another environment. Set production `PUBLIC_BASE_URL` to the deployed HTTPS origin and `SECURE_COOKIES=true`.

Apply `node scripts/db/apply-migration.cjs email` after the site support migration, then build and restart the server. Startup checks the new tables. Verify the target database after applying it.

After the signup/marketing migration, run `node scripts/db/apply-migration.cjs email-polish` on existing installations. It adds the persisted first-correction waiver to both verification flows. One address correction may skip the minute wait; later corrections and reloads preserve the cooldown, and every send still counts toward the hourly limit.

New feedback and support requests enqueue one notification within the same transaction as the request. A worker sends one pending notification every 15 seconds. Provider failures retry every ten minutes, up to eight attempts; request submission remains saved. Resend idempotency keys prevent duplicate sends during retries. Alert content contains the category and subject; review the full message in the admin area. Existing requests are not backfilled. Support reply notifications are outside this implementation.

Check failures with `SELECT id,request_id,attempts,next_attempt_at FROM email_outbox WHERE sent_at IS NULL;`. After resolving delivery configuration, reset attempts and next_attempt_at for the intended failed rows. Retrying more than 24 hours after an uncertain send may duplicate mail because provider idempotency expires.

Provider DNS and receiving routes are deployment-specific. Verify the sender domain with the provider and test delivery in the target environment; the repository cannot establish current DNS or inbox configuration.

## Marketing

Signup always verifies email before an account is activated. The existing guest session remains active during this step. An optional, unchecked checkbox records marketing consent; a verified opt-in queues a welcome email about three minutes after verification. Set `MARKETING_POSTAL_ADDRESS` before welcome delivery is enabled. Every message contains a signed-free random unsubscribe URL that works without login and also honors standard one-click unsubscribe headers.

Use Resend's Broadcast editor for occasional campaigns. Create a Resend API key with Contacts access and set it as `RESEND_MARKETING_API_KEY`; the app then syncs each verified player's subscription state to Resend Contacts. Build and schedule Broadcasts in Resend, including its unsubscribe placeholder/footer. Do not use the transactional key for this: a send-only key cannot perform contact synchronization. The app's own welcome message is transactional and independently honors the player preference.

Broadcast opt-outs are checked when email preferences are opened and immediately before a welcome message is sent. Provider failures leave the welcome queued rather than ignoring the unsubscribe check. New local preference changes sync first. Contact updates use Resend's update endpoint so an existing contact is updated correctly; failed welcome sends stop after five attempts.

## Friends

`src/server/services/social/friendService.js` owns friend codes, requests, friendships, recent-player suggestions and direct messages. `src/client/friends/friendsPanelController.js` owns the panel; route/socket modules authenticate transport before calling the service. Guests cannot use friends. Apply the `friends` migration helper before enabling these flows; see [database](database.md).

Friends show live activity while connected and a relative last-seen time while offline, with the exact local time on hover in the list and direct-message header. Apply `npm run migrate:apply -- friend-last-seen` before restarting with this change. `users.last_seen_at` persists activity independently of party membership, refreshes every ten seconds while active, and records transitions offline. Accounts without recorded activity show “Last seen unknown” until their next visit.

Privacy settings live in `user_privacy_settings` (no row means defaults); `src/shared/social/privacy.cjs` defines the fields and `friendService` enforces them. Players choose who can send friend requests (everyone, recent players with 2+ matches in 14 days, or no one), whether friends can message them or send party invites, whether friends see their last-seen time, whether read receipts are shared (both players must allow them; typing indicators show unless the friend has messages off), and whether they appear in other players' suggestions. They are edited in Settings → Privacy and, for friend requests, in the friends Add tab. Apply `npm run migrate:apply -- privacy-settings` before restarting with this change; the friends list query joins the table.

## Name changes

Permanent accounts pay 50 gems per name change at `/profile/change-username`. A successful change starts a one-calendar-month cooldown (month-end dates clamp to the last day of the next month). Balance, name, party membership name, and cooldown update in one transaction under an account row lock. Invalid or taken names, insufficient gems, and submitting the current name do not charge or restart the cooldown. The profile form shows the cost and next eligible local date.

Apply `npm run migrate:apply -- name-changes` before restarting the server. Existing accounts start with no cooldown; signup names remain free.

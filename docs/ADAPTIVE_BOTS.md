# Adaptive matchmaking bots

Duels supports server-run bots on Lushy Peaks, Mangrove Meadow, and Serenity. No bot accounts, browser sessions, or inference API calls are created. Bank Bust and mid-match disconnect replacement are not supported.

## Deploy and enable

1. Drain active matches and stop old matchmaking workers, then apply `migrations/2026-09-03_adaptive_bots.sql`. This adds temporary bot participants and converts queued ratings to account trophies without resetting wait times.
2. Deploy the server and the client build together. Existing bot-only vertical physics has been removed from the client, so mixed client/server versions should not be used.
3. Start with the existing admin **Fill with bots** control in a Duel queue. Explicit unlimited-health testing remains available only through that admin control.
4. For automatic-fill testing, add `"bots": { "enabled": true, "rolloutPercent": 100 }` to `runtime-overrides.json`, retaining its other settings, then restart the server. This enables every Duel queue. For a limited production cohort, use `10` instead: cohorts are assigned consistently by queued user/party ID, so 90% of accounts/parties will receive no automatic bots, even after repeated queue attempts. Increase the percentage after gameplay and capacity checks.
5. Disable new fills with `"enabled": false`. Existing rooms continue to completion. Configuration changes through the existing runtime-config service take effect immediately; direct file changes require a restart.

Defaults are disabled with zero rollout. A missing bot table does not prevent human-only rooms from loading, but enabling bots requires the migration.

### If automatic filling does not start

- Confirm the running server has loaded `enabled: true` and `rolloutPercent: 100` for testing. Editing the JSON file alone does not reload it; restart the server, then leave and rejoin a Duel queue. The first bot stages starting from 5 seconds at a randomized time, and the ready check follows once all seats are filled.
- Run the **entire** migration file with old matchmaking workers stopped. Warning 1050 (`Table already exists`) is harmless on reruns. The migration temporarily disables `SQL_SAFE_UPDATES` for its backfill transaction and restores the connection's previous setting afterward; no Workbench preference change is needed. An older copy can fail with error 1175 before clearing stale `claimed_by` values, which exclude those tickets from matchmaking.
- If the queue still does not fill, inspect the server console for `[mm] tick failed:`. Successful assembly logs `[match:assembled]` with human and bot counts. Bank Bust does not support automatic bots.

## Queue and participant contracts

- Human-first grouping preserves complete party tickets and their team relationships. Compatibility uses account trophies: a 100-trophy window expands 15 trophies per second up to 400.
- The oldest eligible ticket anchors each draft. Bot seats become available starting from 5 seconds at randomized intervals (5.0s to 8.5s for seat 1, followed by 1.0s to 3.0s random intervals for subsequent seats) to prevent players from anticipating bot arrival times. Humans can replace draft bots until the roster commits. Loading and the existing countdown follow matchmaking.
- All assembly paths lock and revalidate tickets in one transaction. Cancellation before lock prevents assembly; cancellation after commitment cannot undo a found match.
- Roster entries add `participantId` and `isBot`. Humans retain `user_id`; bots have `user_id: null`. Existing snapshot keys and socket event names remain compatible. Bot identity is explicit, never inferred from the display name.
- Names come from an expanded pool featuring troll names (`SkillIssue`, `TouchGrass`, `DeleteTheGame`, etc.), gamer tags, procedural adjective-noun combinations (over 4,200 unique pool entries), a chance to sample registered real usernames from the database, and occasional guest default usernames (`Guest` or `GuestXXXXXX`), without duplicates among match participants. Legacy numbered `BOT` and `BOT ULTRA` labels are excluded even when supplied by database username sampling. Characters are chosen uniformly from all six available characters, using default skins. Bot level is the rounded median human selected-character level; skill uses the mean human trophies.
- Combat ownership uses participant IDs. Human socket input remains authenticated by its socket; a socket cannot claim to attack as a bot. Bots have server-side ammo and special charge and use the same damage/effect machinery.
- Human match rewards remain unchanged. Bot combat stats appear in results, but bots receive no account rewards. Bot rows are deleted on finish/cancellation/abandonment, with a minute-based stale-record sweep for failures. No name-based deletion of user accounts occurs.

## Physics, navigation, and tuning

`src/shared/duelMaps.json` owns Duel layouts, collision flags, texture dimensions, spawn anchors, bounds, and powerup points. Both map rendering and server collision use it. The map editor's **Export Map Snippets** action exports a replacement entry for this catalog on Duel maps. Preserve/update anchor references when removing or reordering platforms. New textures require accurate source dimensions; the editor exports them.

`src/shared/characterFrames.json` records base-skin idle frame dimensions, paired with the existing shared body and movement tuning. Refresh dimensions when replacing base character artwork. Bots use fixed-step acceleration, drag, gravity, ground/wall jumps, directional collision, and the same body offsets as the character implementation. They use server snapshots for both axes on clients.

Navigation edges simulate real movement, including walking/drops with and without wall jumps. Samples inside solid obstacles are rejected. Tactical and recovery goals require a route to the actual destination coordinate, not just membership in a reachable platform; raw platform centers inside walls are never used as recovery goals. Route cost includes approaching takeoff, and different landing positions on a platform remain distinct search states so a wall can be bypassed by climbing and returning on its other side. Graphs are cached by geometry object, character, and movement modifiers.

At takeoff, the executor validates the route from the actual body state rather than assuming its velocity and wall-jump timing exactly match the graph sample. Landing validation includes braking and turning into a stable stance; touching a platform for one frame is insufficient. Travel owns steering until this landing completes. Optional wall-play no longer cancels a verified traversal. A failed sample temporarily blocks that specific edge rather than every route between the two platforms. Displacement still cancels an invalid traversal and invokes airborne recovery.

Tactical goals and ledge braking share facing-aware stance limits, scaled to narrow platforms. This matters on Lushy Peaks, where the tall side platforms require indirect climbs and small stances exposed contradictory edge corrections. Its upper powerups also expose an arrival mismatch: a bot can stop within its ordinary walking tolerance yet remain just outside the 70-pixel pickup radius because of vertical separation. Pickup goals now validate collection reach, use radius-based horizontal precision, and execute a verified hop for elevated pickups. Uncollectible stances are excluded from pickup and death-drop scoring. Last-seen search points and shockwave escape points use the same destination reachability checks. Adjacent coplanar colliders count as continuous walking ground. Knockback, hooks, poison, and failed recovery can still kill a bot.

The decision controller samples visible nearby opponents and projectiles, delays reactions, and scores attacks, spacing, recovery, regeneration, and pickups. Each bot has reproducible personality and aim variation. Difficulty interpolates through trophy anchors at 0, 500, 1,250, 2,000 and 4,000, with reaction ranges of 300–420, 220–310, 150–220, 130–190 and 105–170 ms respectively. It caps at 4,000. Maximum skill retains aim error, missed opportunities and imperfect dodging; aggression is a seeded personality trait rather than an increasing trophy bonus. Higher tiers also lead targets more accurately, dodge more reliably, reconsider tactics faster, and make fewer attack mistakes. Mistakes occur at attack opportunities, not as per-frame random inputs. High-tier strength remains a tuning target rather than a forced outcome.

Movement candidates are reconsidered roughly once a second, comparing the current goal against alternatives under the same scoring rules. Small score improvements retain the current goal; serious pressure, recovery transitions, poison, lost pickups and invalid routes can interrupt it. Safe routes remain committed between decisions. A brief opening pause and pauses on arriving at exploration goals remain; periodic mid-route idle pauses and random kite timers have been removed. Staged pursuit can hold only within attack range, and never while approaching a route takeoff. Bots hold useful firing positions instead of constantly pursuing the opponent's exact location. Character spacing, nearby enemies, travel cost, and height determine which ground they seek. Walking/drop routes compete with jumps; seeded route preferences and temporary avoidance of failed edges provide alternate paths.

Bots begin retreating at roughly 38–43% health, depending on tactical skill, and remain cautious until roughly 69–75%. Retreat scoring favors increasing clearance as health approaches zero and evaluates exposure along the whole route, including the walk to takeoff. Crossing a pursuer is penalized even if the eventual destination or healing pickup looks attractive; incidental loot does not interrupt an escape under pressure. Retreat routes are reconsidered when pursuers get close. Counterfire prioritizes the closest attacker, uses shorter attack hesitation, and has no additional retreat-only firing cooldown. Normal ammunition, attack cooldowns and reaction limits still apply. Once clear of pressure, bots stop counterfiring so regeneration can begin. Useful reachable powerups can interrupt a fight, and a weakened opponent can draw focus away from a healthy target. Projectile dodges work at every trophy band with different success chances. Optional escape hops require simulated safe landings, and wall recovery includes brief slides and occasionally late jumps. A progress watchdog also handles missing routes and zero movement intent, while excluding deliberate pauses.

Charged supers are held briefly so the full meter and character-specific positioning create pressure. Ninja waits for aligned, weakened, or grouped targets; Thorg activates rage upon entering melee; Draven requires close or clustered enemies before anchoring Inferno; Wizard favors moments when the team needs buffs; Huntress prefers a stable mid/long-range volley; and Gloop hooks retreating or vulnerable targets from useful range. Bots preserve offensive supers during retreat; defensive Wizard/Thorg buffs remain available when their normal conditions justify them. Charged-super spacing cannot push a bot beyond its useful basic range.

When a bot has at least a modest health lead over its target, it gives that wounded opponent higher target priority, reduces defensive spacing, and closes to a more aggressive version of its character's preferred range. Its own retreat rules still take priority.

Basic attacks add a skill- and personality-scaled hesitation after cooldowns and reloads, with occasional quicker follow-ups. Bots therefore do not fire on the exact frame every new ammo charge becomes available.

Perception measures returning-projectile velocity from observed motion and tracks public attack windups. Human Huntress arrows have separate temporary flight records for bot perception; these records cannot apply damage or effects. Predictive aiming includes target velocity, projectile travel time, and attack startup. Direct-fire characters avoid firing through solid geometry. Recent attackers receive target priority, while executable shots and weak opponents can trigger target switches. Decisions never read invisible opponents' live positions.

## Team decision ownership

The existing vanguard, anchor, support, flank, defend and recover roles remain flexible guidance. Anchors rotate into useful fighting range instead of anchoring to an empty spawn. Formation and assigned-target influence scale with tactical awareness; stronger teams reconsider shared plans sooner. Casualties and health changes still interrupt plans. Team and individual recovery use the same threshold function and recovery hysteresis.

Flankers can split pressure onto another nearby healthy opponent, while wounded opponents can draw shared focus. Support/defend assignments retain combat target priority. Nearby allies affect outnumbering and spacing, and a teammate already collecting a powerup normally gets priority; urgent healing can override that preference. Fresh shared observations can direct a bot toward team activity outside its own perception range, without reading hidden enemy coordinates.

## Verification and telemetry

- `npm run test:bots`: deterministic queue, identity, physics, combat, lifecycle, rewards, and concurrency checks using isolated in-memory fixtures; no live database required.
- `node --test tests/powerups.test.js`: regression coverage for shared powerup effects.
- `npm run simulate:bots -- --seconds=45 --seed=17`: six-character headless smoke matches on all Duel maps, with per-bot damage, actions, recovery/fall counters, tick costs, and serialized packet volume. Optional `--map=1`, `--players=2`, and `--trophies=2000` narrow a scenario. This is a simulation benchmark, not a production capacity certification.
- `npm run simulate:bots -- --matrix --seconds=30`: 81 seeded scenarios across three Duel maps, three team sizes, three trophy tiers and three rotated character rosters. Each scenario resets its simulation clock and reports its roster, active time, mode time, distance moved and longest blocked interval. Use `--characters=huntress,gloop` with a seed/map/rating to reproduce a roster.
- `[match:assembled]` logs queue wait and human/bot counts. `[bots:match-result]` logs winner, human trophy ratings, bot difficulty and behavior counters, and bot processing costs. Game hub stats include active bot counts and timing totals.

Behavior counters include deliberate/positional idle time, stalled movement time, dodges, jumps, optional escape hops, wall pauses, target switches, retreats, and pickup goals. `tests/botBehavior.test.js` covers holding ground, retreat/counterfire, actual pickup collection, target switching, ranged perception/dodging, leading shots, and unreachable-target recovery. `tests/botCoherence.test.js` also executes 120 complete low-skill navigation cases across every Duel character/map destination, plus decision commitment, Wizard spacing, team pickup priority, defensive buffs, naming and the 4,000-trophy cap. The seeded simulation includes powerup spawns and collection.

Cleanup validation (2026-09-06): `node --test tests/*.test.js tests/*.test.mjs` passed all 298 tests. The 120 complete zero-trophy route cases reached their destinations and settled safely. The 81-match, 30-second matrix covered 324 bot runs with zero unforced falls, a longest actionable blocked interval of approximately 2.02 seconds (1.95 seconds on Lushy Peaks), and a worst scenario p95 tick cost of 2.85 ms on the local test machine. Every bot alive for over ten seconds attacked. These are seeded headless results; freeze/control locks are excluded from the actionable-blocked metric, and they do not establish live balance or performance under production load.

Before broad rollout, test against MySQL with simultaneous queue/cancel/ready operations; play mixed human/bot matches from two browsers on every Duel map; inspect movement and attack effects under latency; confirm cleanup after abandoned matches and restart; and measure capacity on deployment hardware. Use aggregate results by trophy tier to tune high-tier win rates and reduce unforced falls/stalls. Humanlike play and high-trophy challenge still require human playtesting.

### Sudden-death navigation

Rising lava/poison is a damage cost, not an impassable boundary. Graph routing retains submerged stepping stones and brief descents, and traversal/landing validation checks physical support rather than rejecting contact with poison. Route costs include exposure during takeoff approaches and traversal; tactical scores also include the final walk and a short stay at the destination. Exposure uses the server's player-origin damage boundary, configured damage rate, and projected rising level. Remaining health makes likely lethal detours much more expensive, while nearby enemies and observed charging motion can justify taking poison damage to escape. Dodge scoring also includes poison exposure. These are estimates based on observed motion, not guarantees of enemy actions.

Being near poison no longer cancels a takeoff approach on every think. Bots reassess hazardous goals at their normal decision cadence and can still change course for combat pressure or invalid routes. Air recovery retains submerged landing surfaces so poison avoidance cannot remove the only way to avoid a fall.

Run `node scripts/simulate-bots.cjs --matrix --seconds=30 --sudden-death=10` to start ten seconds into sudden death and exercise the live rising level and poison damage across the map/team/trophy matrix. Omit `=10` to start at the beginning of sudden death.

Sudden death no longer replaces combat positioning for the whole phase. Chasing, attack-angle scoring, character spacing, and ineffective-position recovery remain active; escape mode applies only when gas is close to the bot. Elevation bias and additional escape-pressure scoring do not influence dry, unthreatened routes just because sudden death has started. At 90% world-height coverage (poison Y <= 100 for the 1000-unit world), navigation and dodge/tactical scoring ignore gas and use normal routes again. Crossing that threshold immediately clears stale escape and idle commitments. Server poison damage is unchanged.
